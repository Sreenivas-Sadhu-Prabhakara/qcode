Design reference · v0 · harness in development

Claude plans.Your local Qwen executes.A cross-vendor jury gates it.

qcode is a local coding harness. Claude designs the flow and writes the tests; a fast local Qwen writes the code in a background git worktree; then a three-vendor jury — Qwen and Codex blocking, Gemini advising — tries to break it before anything merges.

Why it's built this way

Each model does what it's best at

Claude is excellent but costs tokens per step. Local Qwen is fast and private but weaker. qcode splits the work so the expensive model plans once and then steps out — never grinding the loop, never reviewing — while the cheap local one does the bulk of the writing and two other vendors sit the jury.

Planner

Claude designs the flow

Claude turns your task into a step-by-step plan and writes a failing acceptance-test suite first. It plans once, then steps back — it isn't in the hot loop.

Executor

Qwen writes the code

The local Qwen3-Coder MoE (~82 tok/s on an M2 Max) writes and revises code against the tests in a throwaway worktree — fast, private, and free of per-token cost.

Reviewers

A cross-vendor jury decides "done"

Qwen and Codex each independently try to refute the diff — running tests and types, not just reading — and either can veto. Gemini adds a third frontier lens as advisory. Codex and Gemini never saw it written; Qwen re-attacks its own diff in a fresh context. A real defect loops the job back.

The pipeline

One job, five stages, one queue

You submit a task and get a job id instantly. A background daemon runs jobs one at a time (the local model is single-lane) and reports status back.

Under the hood

Wraps proven parts, builds only what's new

The executor is Aider in architect/editor mode — it already ships the hard parts (SEARCH/REPLACE edits, a test-fix loop, repo-mapping). qcode owns the genuinely new layer: the queue, the worktree isolation, and the cross-vendor adversarial gate.

planner

Claude via the CLI

Shells out to claude -p — reuses your Claude Code subscription, no separate API key. Emits a validated JSON plan and the acceptance oracle.

executor

Aider, editor = local Qwen

--architect with --editor-model openai/qwen pointed at LiteLLM :4000. Runs --no-auto-commits in the worktree with --test-cmd.

reviewers

Qwen + Codex block · Gemini advises

Qwen (local) and codex exec block — independent, execution-grounded, each refuting against the acceptance criteria; a defect only counts with a concrete failing scenario. gemini -p adds an advisory third lens. All reuse subscription logins, no API keys.

queue

File-based daemon

Jobs live as files under ~/.qcode/jobs/<id>/. The filesystem is the queue and the status API — no socket, serial by construction, crash-durable.

Usage

The commands

Submit and walk away; check back whenever. A job goes queued → running → done or blocked.

CommandWhat it does
qcode run "task" --repo <path>Plan → execute → review a task in the background. Prints a job id and returns immediately.
qcode status <id>Show a job's current stage, loop count and result.
qcode watch <id>Live-follow a job to completion.
qcode lsList all jobs and their states.
qcode logs <id>Tail the executor + reviewer transcript for a job.
qcode diff <id>Show the reviewed change set for a finished job.
qcode merge <id>Apply a done job's diff onto your branch (never automatic).
qcode cancel <id>Stop a queued or running job and clean up its worktree.
Setup

What it runs on

qcode is the thin orchestrator; these are the pieces it drives. All local except the Claude planner and the Codex + Gemini reviewers, which reuse your existing subscription logins — no API keys.

# prerequisites
• Node 20+            # the qcode CLI + daemon (TypeScript)
• claude CLI          # planner: plan + failing oracle tests (claude -p)
• aider               # the executor engine (pip/uv install aider)
• Qwen on :4000       # local MoE via LiteLLM → MLX (Qwen3-Coder-30B-A3B) — executor + blocking reviewer
• codex CLI           # blocking reviewer (codex exec · your subscription)
• gemini CLI          # advisory reviewer (gemini -p · your subscription)

# once built:
npm i -g qcode
qcode run "add a --json flag to the export command" --repo ~/myproject
› queued job a1b2c   # check back with:  qcode watch a1b2c

Local model verified at ~82 tok/s warm on a 64 GB M2 Max · single-lane, so jobs run serially by design.

Design principles

Why it can trust a weaker model

01

"Done" is objective

Claude writes the failing tests before any code. The executor grinds against ground truth, not vibes — so a fast, weaker model can be trusted to iterate on its own.

02

Review is execution, not opinion

The skeptics run the tests, types and linters and try to construct a breaking input — an adversary that executes beats one that only reads.

03

Three vendors, three blind spots

The gate spans three vendors — Alibaba's Qwen, OpenAI's Codex, Google's Gemini — with no shared training, so no shared blind spots. Codex and Gemini never saw the code written; Qwen re-attacks its own diff in a fresh context, prompted to refute, not defend. Qwen and Codex can each veto; Gemini rides along as a free frontier lens. Diversity and independence, not strong-versus-cheap, is what catches the defect the author couldn't see.

04

Honest about status

No auto-merge, no silent truncation. A job is done only when tests and both blocking reviewers (Qwen + Codex) pass; otherwise it's blocked with the evidence — and Gemini's advisory notes — attached.

Roadmap

Ship the keystone first, stage the rest

Each release earns its keep before the next. Only the keystone — objective, execution-gated "done" — is a mistake to defer.
